# 技术设计

## 1. 设计目标

1. **上帝视角唯一可信**：所有游戏状态只存在于引擎内部，agent 永远拿不到全局状态。
2. **信息隔离可证明**：视角不是"手写裁剪"，而是从**带可见性标签的事件日志**里机械地过滤出来的。
   只要事件的 `audience` 标对，就不可能泄密。
3. **agent 可替换**：引擎只依赖 `Agent.act(view) -> dict` 这一个接口。规则 bot 和 LLM 可以混合同场。
4. **可复现**：`--seed` 固定发牌和所有随机决策；一局游戏可以完整序列化成 JSON 复盘。
5. **零依赖可跑**：默认后端是内置规则 bot，`python3 run_game.py` 开箱即用，不需要网络和 API key。

## 3. 核心抽象：带可见性的事件日志

一局游戏 = **一条只追加的事件流**。引擎不直接给 agent "状态"，而是给它
"**它有权看到的那部分事件**"。

```python
@dataclass
class Event:
    seq: int                  # 全局单调递增序号
    day: int
    phase: str
    type: str                 # "speech" / "vote" / "death" / "seer_result" / ...
    actor: int | None         # 行动者座位
    targets: list[int]
    audience: Audience        # PUBLIC | WOLVES | PRIVATE | GOD
    visible_to: list[int]     # audience=PRIVATE 时，能看到的座位列表
    text: str                 # 该事件对可见者呈现的文字
    payload: dict             # 结构化数据
```

### 四种可见性

| Audience | 谁能看到 | 例子 |
|---|---|---|
| `PUBLIC` | 所有 12 名玩家（含已死亡） | 发言、投票、死讯、遗言、警长竞选 |
| `WOLVES` | 所有狼人（含已死亡的狼人） | 狼人频道发言、刀人投票、刀人结果 |
| `PRIVATE` | `visible_to` 中列出的座位 | 预言家验人结果、女巫的刀口告知与用药、猎人开枪状态、发牌 |
| `GOD` | 无人（仅复盘和日志） | 非法动作回退、随机数决策、真实身份表 |

### 过滤函数（`events.py`）

```python
def visible_to_seat(event, seat, is_wolf) -> bool:
    if event.audience is Audience.PUBLIC:  return True
    if event.audience is Audience.WOLVES:  return is_wolf
    if event.audience is Audience.PRIVATE: return seat in event.visible_to
    return False   # GOD
```

> **这是整个信息隔离的全部逻辑。** 只有 4 行。任何"泄密 bug"都只可能是
> 某条事件的 `audience` 标错了 —— 这一点由 `tests/test_visibility.py` 全量覆盖：
> 遍历所有事件，断言"任何非狼玩家的视角里不包含任何 `WOLVES` 事件"、
> "任何玩家的视角里不包含别人的 `PRIVATE` 事件"、"没有任何视角里出现别人的真实身份"。

## 4. 视角生成（`views.py`）

引擎在每次向某个 agent 索要动作之前，都会现场构造一份 `PlayerView`：

```python
build_player_view(state, seat)  ->  PlayerView    # ×12
build_wolf_team_view(state)     ->  WolfTeamView  # ×1
```

`PlayerView` 由 5 块组成（详见 `docs/04-视角与上下文.md`）：

| 区块 | 来源 | 说明 |
|---|---|---|
| `identity` | 直接读 state，只读自己那一格 | 我的座位 / 角色 / 阵营 / 角色专属知识 |
| `public_state` | 从 state 派生出**公开可推**的部分 | 天数、阶段、存活名单、警长、票型历史、死亡记录、公开宣称 |
| `timeline` | `event_log.visible(seat)` | 我能看到的全部事件，按时间排序 |
| `wolf_team` | 仅当我是狼人时挂上 | 狼队共享视角（同一份对象） |
| `legal_actions` | `actions.legal_actions(state, seat, phase)` | 我现在能做什么 + 参数范围 |

**关键不变式**：`build_player_view` 只允许访问
`state.players[seat]`（自己）+ `state.public_*`（公开派生量）+ `event_log.visible(seat)`。
它**不读**别人的 `player.role`。代码里通过一个 `_PublicPlayer` 投影结构强制这一点：
公开玩家对象只有 `seat / name / alive / is_sheriff / revealed_role / public_claim` 字段，
根本没有 `role` 属性，写错了会直接 `AttributeError`。

## 5. Agent 接口

```python
class Agent(Protocol):
    name: str
    def act(self, view: PlayerView) -> dict: ...
```

- 引擎把 `PlayerView` 交给 agent，agent 返回一个 dict 形式的动作。
- 返回值经过 `actions.validate(state, seat, action_type, raw)`：
  - 合法 → 执行
  - 非法 → 带着错误信息重试（LLM 后端最多 2 次）→ 仍失败则安全回退

### 两个内置后端

| 后端 | 说明 |
|---|---|
| `heuristic` | 纯 Python 规则 bot。狼人会协同刀神、预言家会报验人、好人按"被指认次数"投票。零依赖、毫秒级跑完一局，用于回归测试和流程验证。 |
| `llm` | 调用 Claude Messages API（`claude-opus-5`），用 `output_config.format` 的 JSON Schema 强约束返回结构。每个座位维护**自己独立的对话历史**，天然不共享上下文。 |

可以混合：`--backend llm --llm-seats 1,2,3`（只有 1/2/3 号用 LLM，其余用规则 bot），
方便低成本地做"一个 LLM 打一桌 bot"的实验。

### LLM agent 的上下文组装

```
system  : 角色卡（规则全文 + 我的身份 + 我的阵营目标 + 输出格式约束）
messages: [ {user: 第1夜视角快照 + 请求动作}, {assistant: 我的动作 JSON},
            {user: 第1天视角增量 + 请求动作}, {assistant: ...}, ... ]
```

- **system 保持逐字不变** → 命中 prompt cache，成本大幅下降。
- 每回合只追加**自上次以来的新事件**（增量），不重发整份 timeline。
- 狼人 agent 的 user 消息里额外拼上**狼队视角**区块。

## 6. 数据流全景

```
                        ┌──────────────────────────┐
                        │      GameState (上帝)     │
                        │  真实身份 / 药 / 验人记录  │
                        └────────────┬─────────────┘
                                     │
                        ┌────────────▼─────────────┐
                        │   EventLog（带可见性标签） │
                        └────────────┬─────────────┘
              ┌──────────────────────┼──────────────────────┐
              ▼                      ▼                      ▼
     visible(seat=1)         visible(seat=2)   …   visible(seat=12)
              │                      │                      │
     ┌────────▼───────┐     ┌────────▼───────┐     ┌────────▼───────┐
     │ PlayerView #1  │     │ PlayerView #2  │ …   │ PlayerView #12 │
     └────────┬───────┘     └────────┬───────┘     └────────┬───────┘
              │                      │                      │
       + WolfTeamView（仅狼人挂载，4 个狼人共享同一份）
              │                      │                      │
     ┌────────▼───────┐     ┌────────▼───────┐     ┌────────▼───────┐
     │   Agent #1     │     │   Agent #2     │ …   │   Agent #12    │
     └────────┬───────┘     └────────┬───────┘     └────────┬───────┘
              └──────────────► Action ◄───────────────────┘
                                     │
                          actions.validate() → engine 执行 → 追加新事件
```

## 7. 复现与产物

一次运行会产出：

```
runs/<timestamp>/
├── config.json         # 板子 / seed / 后端配置
├── events.jsonl        # 全部事件（含 GOD 级），完整上帝视角
├── result.json         # 胜负、存活名单、真实身份表
├── replay.md           # 人类可读的文字战报
└── views/
    ├── seat_01.json … seat_12.json   # 每个座位在游戏结束时的完整视角
    └── wolf_team.json                # 狼队视角
```

`--dump-views` 会在**每个决策点**都快照一次视角，产出
`views/turn_0007_seat_03.json` 这样的文件，用来逐帧检查信息隔离。
