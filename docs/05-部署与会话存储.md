# 部署与会话存储

两个问题一起回答：**agent 跑在哪**，以及**会话存在哪**。
它们耦合在一条约束上：

> **玩家离场就销毁容器，但所有会话必须保留下来复盘。**

---

## 1. 四种部署模式

引擎本身对容器一无所知 —— 它只认识 `runtime.act(view) -> action`。
所以同一套规则在哪跑出来都一样，换模式只换一个参数。

| 模式 | 一个座位 = | 隔离级别 | 用途 |
|---|---|---|---|
| `inprocess` | 一个 Python 对象 | 无（同进程） | 测试、跑批统计，毫秒级 |
| `subprocess` | 一个 OS 进程 | 进程 + 独立 memory 目录 | 没装 Docker 时的真隔离；CI 里验证容器契约 |
| `docker` | 一个容器 | 容器 + cgroup 限额 + 独立卷 | **单机部署** |
| `k8s` | 一个 Pod | Pod + 资源限额 + 独立 PVC | **集群部署** |

```bash
python3 run_game.py --deployment subprocess          # 命令行
python3 run_server.py                                # 网页里"高级选项 → 部署模式"选
WEREWOLF_DEPLOYMENT=k8s python3 run_server.py        # 或用环境变量定默认值
```

`subprocess` / `docker` / `k8s` 走**完全相同的 HTTP 契约**，所以
`tests/test_deployment.py` 用 `subprocess` 就能把容器路径的全部逻辑
（起 → 就绪 → act → 抓会话 → 销毁）在 CI 里验一遍，不需要真的有集群。

## 2. agent 容器里是什么

一个容器 = 一个座位 = 一个玩家。**容器拿不到 `GameState`，也不知道别人的身份。**

```
  编排端                                agent 容器（座位 N）
    │                                        │
    │  POST /act {"view": {...}}             │  ① PlayerView.from_dict() 还原视角
    │ ─────────────────────────────────────► │  ② 读自己的 /memory/seat_NN/notes.md
    │                                        │  ③ 组装 prompt，调自己的模型
    │ ◄───────────────────────────────────── │  ④ 写回笔记，返回动作
    │                     {"action": {...}}  │
    │                                        │
    │  GET /session   ← 销毁之前必须先调      │
    │ ◄───────────────────────────────────── │  system prompt + 完整对话 + 用量 + 笔记
    │                                        │
    │  docker rm -f / kubectl delete pod     │
    │ ─────────────────────────────────────► ✗  容器没了，但 /memory 卷还在
```

| 接口 | 用途 |
|---|---|
| `GET /healthz` | 就绪探针（k8s `readinessProbe`） |
| `POST /act` | `{view, error}` → 动作 |
| `GET /session` | 导出完整会话，**销毁前必须调一次** |

### agent 的私有 memory

每个座位挂一个卷到 `/memory/seat_NN/`，里面有它自己的 `notes.md`：

- 每回合的 prompt 里会带上「你的私人笔记本（只有你自己看得到）」
- agent 可以用动作里的 `notes_update` 字段更新它
- **卷的生命周期长于容器**：容器被销毁、甚至崩溃重启，笔记都还在
- 其他玩家、其他 agent 永远看不到别人的笔记

## 3. 会话存哪：数据库还是文件系统

**两个都要，按数据形状分。**

| 数据 | 存哪 | 为什么 |
|---|---|---|
| 事件流、每一轮的动作和心路历程、agent 的对话历史 | **SQLite（默认）** | 要跨局查询、要事务性追加、单文件零运维；k8s 下 N 个 Pod 连一个 DB endpoint，比挂 RWX 共享卷简单得多 |
| agent 的私有 memory（它自己写的文件） | **持久卷**（docker volume / k8s PVC） | 那是任意文件，塞进 DB 很别扭；而且卷本来就该活得比容器长 |

```bash
python3 run_game.py --store sqlite:runs/werewolf.db   # 默认
python3 run_game.py --store files:runs                # append-only JSONL，不想上 DB 时用
python3 run_game.py --store none:                     # 不持久化（跑批统计用）
export WEREWOLF_STORE=sqlite:/data/werewolf.db        # 或用环境变量
```

### 两条硬规则

**① 边跑边写。** 每条事件、每次决策**立刻**落库，不是跑完一次性 flush。
否则进程崩了、容器被杀了，这一局就什么都不剩。

**② 销毁前先抓。** `RuntimePool.release()` 的顺序永远是
`snapshot_session()` → 写进存储 → 销毁容器。顺序反了就永远拿不回会话，
所以 `tests/test_deployment.py` 有一条专门的测试盯着这个调用顺序。

### 表结构

```sql
games          (id, created_at, finished_at, status, deployment, config, lineup,
                winner, end_reason, days, result)
events         (game_id, seq, day, phase, type, audience, actor, text, body)
turns          (game_id, turn, attempt, seat, role, day, phase, action_type,
                accepted, error, thought, action, latency_ms)
agent_sessions (game_id, seat, backend, model, role, system_prompt, messages,
                usage, memory_uri, released_at, release_reason)
```

`agent_sessions.memory_uri` 只记卷的位置，卷本身不进 DB。

换 Postgres 只要照着 `werewolf/store/base.py` 的 `SessionStore` 协议再写一个实现，
其余代码一行不用改。

## 4. 座位的生命周期

**死了不等于能立刻拆。** 被票出的还要留遗言、猎人还要开枪、警长还要移交警徽。
正确的释放时机是"该座位再也不会被 `ask()` 到"：

```
玩家被票出
   │
   ├─ 遗言
   ├─ 警徽移交 / 撕毁
   ├─ 猎人开枪（如果他是猎人）
   │     └─ 被枪杀者：同样走完这一套才释放
   │
   └─► 到这里他所有的后续动作都处理完了
          ① GET /session   把会话抓出来写进会话库
          ② 销毁容器 / Pod / 进程
          ③ memory 卷保留
```

白痴翻牌是个例外：他**还活着、还能发言**，所以不释放。

释放原因会跟着会话一起入库，复盘时能看到每个人是怎么离场的：

```
 1号 WITCH     第3天killed      释放原因=killed
 2号 WEREWOLF  第3天exiled      释放原因=exiled
 6号 WEREWOLF  存活             释放原因=game_over
```

## 5. 单机部署（Docker）

```bash
docker build -t werewolf-agent:latest -f deploy/docker/Dockerfile .
python3 run_server.py        # 网页里部署模式选 docker
```

编排端会用 docker CLI **按需**起容器，并在玩家离场时立刻 `docker rm -f`。
每个容器：

- `--cpus 1 --memory 1g` 限额
- `--security-opt no-new-privileges`
- `-v wolf-<game>-mem-NN:/memory` —— **销毁容器时不删这个卷**
- 只监听 `127.0.0.1` 上的一个随机端口

想手工把一桌拉起来看看，可以生成 compose：

```bash
python3 deploy/docker/compose.py -n 12 --backend llm > compose.yml
docker compose -f compose.yml up
```

## 6. 集群部署（k8s）

用官方 Python SDK 直接建/删 Pod，详见 [`deploy/k8s/README.md`](../deploy/k8s/README.md)。

```bash
uv sync --extra k8s
kubectl apply -f deploy/k8s/00-namespace-rbac.yaml
kubectl apply -f deploy/k8s/10-orchestrator.yaml
```

每个座位：一个 Pod + 一个 PVC。**RBAC 里故意没有给 `persistentvolumeclaims: delete`** ——
Pod 删掉之后笔记必须还在，编排端根本不该有删卷的能力。清理旧卷是运维按标签做的事：

```bash
kubectl -n werewolf get pvc -l werewolf/game=<game_id>
```

编排端的 Deployment 固定 `replicas: 1`，因为默认会话库是 SQLite 单文件。
要多副本先换 Postgres。
